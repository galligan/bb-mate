# OS-627 first independent feature wave

## Outcome

Bring OS-628, OS-630, and OS-631 to review-ready pull requests without taking
on upstream-dependent work or replacing native bb behavior.

## Current status

Preparation complete; implementation not started.

- Baseline: `main` at `762ba04440ac71f9e7b8957b8993bba0bce9804c`.
- CI: green at <https://github.com/galligan/bb-mate/actions/runs/31187642754>.
- Local verification: format, check, test, and build all pass.
- Preserved user-owned dirt:
  `.agents/notes/2026-08-07/handoff-202608071030-223a1ed0.md`.
- Harness remains unavailable: `@bb/plugin-sdk` is still absent from npm and

## Execution shape

1. OS-628 extracts the passive inspection core into a small shared package and
   produces a versioned, actionable compatibility report.
2. OS-630 stacks on OS-628 because the CLI is the second real consumer of that
   report, discovery, and native-state contract. It must not duplicate the
   inspection model.
3. OS-631 remains independent from main. It creates the browser-safe public
   surface catalog and declaration coverage check without joining the
   compatibility schema to the fixture schema.

The OS-628 → OS-630 source dependency was discovered during preparation and
should be reflected in Linear before implementation begins.

## Constraints

- Native bb owns build, install, dev/reload, validation, runtime, and Connect.
- The CLI may show and invoke native commands, preserving argv, cwd, output,
  signals, and exit status. It must not add another lifecycle.
- Passive discovery reads data only and never imports plugin entrypoints.
- The sibling `../bb` checkout is read-only development evidence and never a
  runtime or test fallback.
- Harness is capability-gated on the selected plugin resolving the official
  testing subpaths.
- Fixture is an approximation; Harness is behavioral; Live bb is the visual
  authority.
- No merge, land, publish, release, repository-visibility change, plugin
  reinstall/removal/reload, Connect mutation, or upstream bb edit.

## Acceptance checks

### OS-628

- Versioned deterministic JSON and concise human report.
- Actionable checks for manifests, artifacts, engines, native state,
  provenance, trust disclosure, and Fixture/Harness/Live availability.
- Native failures retain stderr/exit evidence and a concrete next action.
- Missing published SDK is distinguished from a local dependency/subpath
  failure without pretending an offline resolver proves registry state.

### OS-630

- `bb-mate [path]`, `dev`, `inspect`, `check`, and `live` have focused help,
  parser, discovery, orchestration, and process tests.
- Root, standalone, single-plugin, and ambiguous selection are deterministic.
- Native commands use a spawned resolved `bb` binary, never a shell, and
  preserve native output and exit status.
- Workbench launch uses explicit host/port and does not mutate Connect.
- `live` never installs a plugin implicitly.

### OS-631

- One browser-safe typed catalog covers the 13 public frontend registration
  groups with stable IDs, ownership, trust, mode, state, and interaction data.
- Host-rendered actions describe outcomes rather than counterfeit chrome.
- `experimental_threadList` exclusivity and content-script lifecycle are
  explicit.
- The existing sidebar scenarios become the thread-list catalog entry.
- A Bun-only declaration coverage check fails on missing, stale, or newly
  added public registration groups and never falls back to `../bb`.

## Verification

Iterate with focused package tests and checks. Before each PR becomes ready,
run:

```sh
bun run format:check
bun run check
bun run test
bun run build
```

Use fake native executables for destructive/runtime CLI behavior. Passive
inspection of the current plugin is allowed; do not exercise the live plugin
through install, dev/reload, removal, or Connect exposure.

## Review gate

- A standing reviewer checks continuity across the goal.
- A targeted reviewer checks each issue slice and its acceptance criteria.
- Fix all P0-P2 findings and reasonable P3 findings, then return to the same
  reviewer for the issue fix loop.
- Before final readiness, use the standing reviewer plus a fresh independent
  full-stack reviewer.
- PR CI must be green and review threads resolved before marking ready.

## Completion

Complete when all three PRs are open and ready, their intended stack/base
relationships are correct, focused and aggregate verification passes, local
review has no open P0-P2 findings, remote CI is green, Linear reflects the
actual dependency and review state, and the workspace is reconciled without
claiming the preserved handoff note.

Not complete when only local checks pass, PRs remain draft, CI or review is
open, one issue is missing, or any implementation depends on unpublished SDK
code or the sibling checkout.
